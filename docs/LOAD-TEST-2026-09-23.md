# Methodology

## Scope and method

Authorized production run against quizflow-flax.vercel.app and its existing Supabase Free project. A temporary owner/workspace/quiz isolated synthetic records from customer questionnaires. The fixture had eight required scored questions and required email/consent, without external integrations. All lead addresses used example.invalid. Auth fixture creation confirmed the temporary user administratively without sending an invitation.

Real SSR-issued signed capabilities were used for public analytics, progress updates and submissions. Service credentials were used only in memory for fixture setup, integrity checks and cleanup. No quotas, rate limits, forwarded IP headers or security controls were bypassed. No paid load-testing service was provisioned.

The test increased simultaneous SSR requests through 1/4/8/16, then 32; exercised analytics and progress bursts, 16 simultaneous submissions, duplicate retries, intentional rate-limit rejection and recovery, a six-minute mixed workload (72 complete journeys, one launched every five seconds), then post-load recovery. Cooldowns respected the existing single-IP limits.

Safety stops: 12-second HTTP timeouts, three transport/5xx failures, two consecutive unhealthy/slow health probes, stage p95 above eight seconds, approximately 4,000 requests or 200 MiB response data. Already in-flight requests may finish after a stop threshold. The six-minute workload is bounded to eight concurrent journeys.

## Interpretation limits

This is one load generator and one source IP, with at most 32 simultaneous HTTP requests. It does **not** establish maximum platform capacity, distributed traffic capacity, thousands of simultaneous users, long-duration endurance, DDoS resistance or absolute security. The single-IP submission limit is deliberately preserved. The six-minute workload is a short sustained check, not a multi-hour endurance test.

Browser checks use four Chrome contexts (two desktop-width, two mobile-width) on the same machine without CPU/network throttling. Mobile-width results are not measurements on physical mobile devices. Public browser POSTs were intercepted and marketing providers blocked to avoid modifying real customer data; actual backend writes were covered separately by the isolated fixture. Button-to-next-step timing includes the UI's deliberate transition delay.

No backup/restore drill or external email/webhook-provider throughput was tested. Gift-email delivery and alert-email receipt remain separate operational items.

## Reproduction

`scripts/load-test.mjs` is a **manual production load tool**, never an automatic CI job. It targets this project's production URLs and creates/removes its own temporary user/workspace. Run only one copy at a time, in an approved quiet window, with Node 20+ and authorized credentials supplied through the environment:

- `QUIZFLOW_LOAD_APPROVED=1`
- `QUIZFLOW_LOAD_SERVICE_KEY` (server secret; never commit or log)
- `QUIZFLOW_LOAD_ANON_KEY`

Run `node scripts/load-test.mjs`. It writes request metadata/aggregates to `/tmp/quizflow-load-results.json` and fixture identifiers to `/tmp/quizflow-load-fixture.json`. Credentials and response bodies are not included in these reports. On interruption/kill, cleanup is not guaranteed: use the recorded temporary owner ID to verify/remove only that fixture, and independently confirm cascaded records are gone. Inspect `failures`, `aborted` and integrity/cleanup stages as well as the exit status.
